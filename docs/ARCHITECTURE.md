# 代码边界与扩展点

后端按一次请求或任务的责任组织。`app/api/routes` 负责 HTTP 契约和依赖组装；`app/services` 负责索引、检索与问答规则；`app/rag` 负责文档处理和模型无关的数据结构；`app/agent` 负责固定诊断图及运行轨迹；`app/models` 和 `app/schemas` 分别是持久化与对外数据契约。模型客户端只在 `app/llm` 与相应适配器中构造，业务规则不依赖具体模型供应商。

## 增加或切换模型

`app/api/chat_config.py` 将配置解析为不可变的 `ChatModelConfig`，`app/llm/chat.py` 创建 OpenAI 兼容客户端。回答和诊断适配器共用这一配置与客户端构造，分别保留自己的提示和结构化响应契约。若新供应商需要不同的结构化输出方式，先在 `app/llm/structured_output.py` 增加受测方法，再通过配置选择；不能在路由或业务服务中加入供应商分支。

Embedding 客户端独立于聊天客户端。索引任务记录创建时的处理参数和向量空间标识，worker 验证标识后才发布；检索只读取当前活动版本且标识与当前配置一致的分片。标识由接口 URL、模型名、原生维度和人工维护的 `EMBEDDING_REVISION` 计算。修改其中任一项后，必须重建需要检索的文档；同地址同模型的权重更新也必须提升修订号。API 与 worker 必须使用一致配置。历史任务没有足够信息推断标识，迁移后保留为空并通过重建恢复检索。

## 增加文档处理实现

`app/rag/processing.py` 是处理器工厂。手动实现与 LangChain 实现都输出 `ParsedDocument` 和 `ChunkCandidate`，索引 worker 不需要知道所选解析器或分片器的内部细节。新增实现应遵守来源页码、章节路径、分片顺序和 token 上限契约，并在创建索引任务时保存后端标识和处理版本。`app/services/indexer.py` 依次完成文件校验、解析与分片、批量向量化；领取、续租、失败与原子发布集中在 `app/services/index_store.py`。

## 扩展诊断流程

`DiagnosticWorkflow` 为每次请求持有数据库会话、模型、检索器配置和运行记录器。`DiagnosticOptions` 明确列出租户、知识库及超时参数。四个节点分别执行计划、只读订单查询、规则检索和结果合成；具名路由函数固定了允许的下一步。增加节点时，同时更新图拓扑、轨迹字段和 `backend/tests/test_diagnostic.py` 中的路由及跨租户断言。模型不得直接选择或执行任意工具。

## 事务与引用

文件或模型 I/O 期间不持有数据库读事务。上传和重建索引的写入 service 自行检查租户，不能只依赖 HTTP 路由。分片发布在单个事务中切换活动索引版本。问答与诊断使用同一引用校验函数，只接受本次已授权检索结果中的分片 ID；这保证引用的访问边界，不保证回答的每个语义结论正确。
