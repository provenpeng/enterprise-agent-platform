# 项目背景

企业内部存在大量的：

- 产品文档
- api文档
- 业务/运营规则
- 操作流程/规范
- 退款规则/流程

纯RAG问答主要解决企业私有知识的索引和问答问题，但无法仅靠知识库获取业务实时状态或者外部系统操作的能力

不仅要能查知识库，还要能查订单信息自动作出业务判断，这就需要AI Agent + business tool + workflow，既能查询业务知识，也能调用业务工具完成诊断

# 目标用户

V1只考虑两类

- 业务用户： 运营人员通过自然语言进行知识查询和业务诊断
- 管理员：上传业务文档维护知识库、维护知识库

# 核心用例

1. 运营人员问 “退款规则是什么”
2. 运营人员问 “订单xxx为什么会退款失败”
3. 管理员维护知识库
    - 上传pdf
    - 文档分片
    - 使用嵌入模型向量化
    - 建立索引
    - 知识存储
4. 管理员查看使用情况
    - 原始问题
    - 检索到的文档内容
    - 最终分数
    - 最终引用的片段
    - Agent执行了哪些步骤
    - 调用了哪些工具
    - 工具输入输出是什么
    - 最终回答
    - token使用情况、耗时、错误等指标
    - 使用的模型

# V1功能范围

1. 用户登录，两种角色：固有的管理员和业务用户（不做通用的RBAC权限控制系统）
2. 文档管理
3. LLM对话
4. 对话历史
5. Agent + workflow
6. business tool
7. rag召回
8. 异常追溯
9. token统计
10. 基础的评价

# V1明确不做

1. 复杂的多Agent
2. 复杂的RBAC
3. 大模型微调/优化
4. 分布式向量数据库
5. 移动端
6. 语音合成
7. 图像生成
8. 不接入任何真实的企业生产订单/支付系统，Business tool 只使用模拟业务数据
9. 不引用前公司的任何业务文档、真实用户数据或者商业机密。
10. k8s
11. 复杂可视化的workflow desiner

只做基础功能

# 验收标准

1. 管理员能够创建知识库并上传受支持的文档
2. 系统能完成文档的解析、分块、向量化和索引建立，并展示处理状态
3. 业务用户提出知识性问题时，系统能检索相关知识并返回带来源引用的回答
4. 业务用户询问具体订单问题时能根据问题选择相应的business tool读取模拟业务数据，必要时查询知识库，并生成诊断结果。
5. 管理员能查看一次Agent run的 完整轨迹，包括tool调用、检索结果、耗时、token消耗量、异常
6. 项目提供基础的Evaluation Dataset，可以执行一组固定测试验证Retrieval和Agent核心能力
7. 新用户根据 README配置环境变量后，能通过docker compose up -d 启动主要服务。

# 怎么算成功

1. 功能完整实现
2. 代码架构优雅合理、模块边界清晰，可读性强、易于扩展。
3. 文档完善
